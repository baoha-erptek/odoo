### Defect-2026-05-10-03: gearment.api.log missing sale_order_id + http_status on push failure

- **Step / section**: §6 push to Gearment
- **Symptom**: After 4 `action_push_to_gearment` calls (one per ordertest2 receipt), `gearment.api.log` shows rows with `http_status=0`, `sale_order_id=None`, `direction=False`, and `error_message='404 Client Error: Not Found for url: https://apiv2.gearment.com/integration-handler/api/v3'` — but the actual stdout from the run shows 400 Client Error against `/api/v3/orders/draft`. The recorded URL path does not match what `requests` actually called. Two observability problems: (a) the http_status field is never set to the real status code (400/404), staying at the default `0`; (b) `sale_order_id` back-reference is null so operators cannot trace which order's push failed.
- **Repro recipe**: Confirm a sale.order then call `action_push_to_gearment([id])`. Inspect `gearment.api.log`. The log row's `sale_order_id`, `http_status`, and `direction` will be empty/zero on failure.
- **Suspected cause**: The HTTP-status assignment only happens on the success path of the adapter; the failure handler logs the exception text but does not set `http_status` from `response.status_code` before raising. `sale_order_id` is set elsewhere only when the response includes the right field — failing requests skip that hook.
- **Severity**: MEDIUM — does not block the pipeline (script still passes §6), but operators cannot triage which order failed without grep-walking the chatter.
- **Owner spec**: `specs/004-fulfillment-routing/findings.md` (P4-01 family).
- **Suspected slice**: P4-01-B (adapter contract regen).
- **Hotfix slice**: TBD — proposed `P4-01-FIX-LOG-LINKAGE`. Wire `sale_order_id` + `http_status` on the failure path of `_log_outbound_request` and ensure the URL path stored matches the actual `requests` URL.
- **State**: surfaced (2026-05-10 09:54 UTC).

- **Owner spec**: `specs/004-fulfillment-routing/findings.md` (P4-01 family).
- **Suspected slice**: P4-01-B / P4-01-C / P4-01-D (any).
- **Hotfix slice**: TBD — proposed `P4-01-FIX-DEMO-PAYLOAD`. Two-step: (1) capture request body + response body on a single push by extending api.log to store full payloads (or via temporary curl-equivalent script); (2) align adapter or seed Gearment-side catalog with `DEMO-T-<id>` SKUs OR substitute one real registered SKU for a smoke-test push.
