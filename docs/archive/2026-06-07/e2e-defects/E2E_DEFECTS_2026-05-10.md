### Defect-2026-05-10-03: gearment.api.log missing sale_order_id + http_status on push failure

- **Step / section**: §6 push to Gearment
- **Symptom**: After 4 `action_push_to_gearment` calls (one per ordertest2 receipt), `gearment.api.log` shows rows with `http_status=0`, `sale_order_id=None`, `direction=False`, and `error_message='404 Client Error: Not Found for url: https://apiv2.gearment.com/integration-handler/api/v3'` — but the actual stdout from the run shows 400 Client Error against `/api/v3/orders/draft`. The recorded URL path does not match what `requests` actually called. Two observability problems: (a) the http_status field is never set to the real status code (400/404), staying at the default `0`; (b) `sale_order_id` back-reference is null so operators cannot trace which order's push failed.
- **Repro recipe**: Confirm a sale.order then call `action_push_to_gearment([id])`. Inspect `gearment.api.log`. The log row's `sale_order_id`, `http_status`, and `direction` will be empty/zero on failure.
- **Suspected cause**: The HTTP-status assignment only happens on the success path of the adapter; the failure handler logs the exception text but does not set `http_status` from `response.status_code` before raising. `sale_order_id` is set elsewhere only when the response includes the right field — failing requests skip that hook.
- **Severity**: MEDIUM — does not block the pipeline (script still passes §6), but operators cannot triage which order failed without grep-walking the chatter.
- **Owner spec**: `specs/004-fulfillment-routing/findings.md` (P4-01 family).
- **Suspected slice**: P4-01-B (adapter contract regen).
- **Hotfix slice**: TBD — proposed `P4-01-FIX-LOG-LINKAGE`. Wire `sale_order_id` + `http_status` on the failure path of `_log_outbound_request` and ensure the URL path stored matches the actual `requests` URL.
- **State**: surfaced (2026-05-10 09:54 UTC).

### Defect-2026-05-10-05: Gearment `printing_options[].location_code` opaque validation (post-schema-fix residual)

- **Step / section**: §6 push to Gearment (residual after Defect-2026-05-10-02 schema fix landed)
- **Symptom**: Even with the corrected schema (`legacy_id` instead of `product_id`, `printing_options[]` outer key with `location_code` + `url` inner keys), Gearment `/api/v3/orders/draft` rejects with `data.line_items[0]: A line item must include at least one printing option with location_code front, pocket, back or whole [has_front_back_or_whole_printing_option]` — the validator's accepted values per the error message are exactly what we send.
- **Repro recipe** (captured 2026-05-10 10:18-10:19 UTC, ~12 probes):
  - Outer key probed: `printing_options` (correct), `print_locations`, `placements`, `prints`, `options` — only `printing_options` doesn't trigger "value must contain at least 1 item(s)".
  - Inner location-code key probed: `location_code` (snake_case), `locationCode` (lowerCamelCase), `code`, `location`, `position` — all rejected identically.
  - Inner location-code value probed: `"front"`, `"FRONT"`, `1`, `0`, `"PRINTING_LOCATION_FRONT"`, `"PRINT_LOCATION_FRONT"`, `"LOCATION_FRONT"`, `"PRINT_LOCATION_TYPE_FRONT"` — all rejected with the same error.
  - Companion URL keys probed: `url`, `image_url`, `design_url`, `file_url`, `image`, `imageUrl`, `designUrl`, `printUrl` — all rejected identically.
- **Suspected cause**: Either (a) the Gearment proto3 `location_code` field name follows yet another convention not publicly documented (we exhausted snake_case + lowerCamelCase + ALL_CAPS_ENUM); (b) there is a parallel REQUIRED field on the printing_option object (e.g. `image` MessageType wrapping the URL) that we are missing, causing the deserializer to default the whole object — which then has location_code="" and fails the validation rule; (c) `printing_options` as a JSON array does not deserialize at all, with each element silently dropped.
- **Severity**: HIGH — same as the parent defect 02. The schema-structure fix landed (verified: `oneof_variant_id_legacy_id` error eliminated when `legacy_id` is non-zero), but the production drop-ship flow remains non-functional because we cannot get a single line_item to pass Gearment's printing_options validator.
- **Owner spec**: `specs/004-fulfillment-routing/findings.md` (P4-01-FIX-PAYLOAD-SCHEMA continuation).
- **Hotfix slice**: TBD — proposed `P4-01-FIX-PRINTING-OPTIONS`. Needs offline help: (1) Gearment customer success / API support to clarify the printing_options proto schema; (2) examine a Gearment dashboard-created order via their export API to capture the exact JSON shape that *they* emit (treat as the canonical schema).
- **State**: surfaced (2026-05-10 10:19 UTC). Workaround: parent defect 02 still records the wiring fires + payload is structurally correct; the residual is opaque-API-level.
