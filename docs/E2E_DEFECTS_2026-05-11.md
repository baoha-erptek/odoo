### Defect-2026-05-11-02 — Gearment push exception not caught into gearment.api.log

| Field | Value |
|---|---|
| **Severity** | High |
| **Pipeline stage** | Gearment push |
| **State** | surfaced → triaged |
| **First observed** | 2026-05-11 13:35 UTC |
| **Reproducer** | XML-RPC `sale.order.action_push_to_gearment([id])` for an order whose Gearment payload trips a 4xx. Expected: action returns gracefully, gearment.api.log row created with `http_status=400`, `error_message`, `response_summary`. Actual: Python `HTTPError` bubbles up through XML-RPC; NO gearment.api.log row created. |
| **Suspected cause** | `multichannel_hub_fulfillment/services/gearment_adapter.py:200` — `response = getattr(exc, 'response', None)` — when underlying request raises before logging hook runs, the log-write path is skipped. The FIX-LOG-LINKAGE landed 2026-05-10 only addressed the response-captured path. The exception path is unguarded. |
| **Impact** | (a) Operators see no record of failed pushes — can't audit Defect-05 occurrence rate without log entries. (b) Production observability gap: pushes that fail with network errors / 5xx never get audited. (c) Defect-2026-05-10-03 effectively returns under live API failure conditions. |
| **Routing** | New slice **P4-01-FIX-LOG-LINKAGE-EXCEPTION-PATH** (spec 005). Wrap the `_request`/`raise_for_status` call in `gearment_api_client.py:148` in a try/except and ensure a log row is written (with `http_status` from `exc.response.status_code` if available, else `0`; `error_message` from `str(exc)`) BEFORE re-raising. |
| **Regression test plan** | Phase 2 ORM test that mocks the requests session to raise `HTTPError` with a fake 400 response. Assert (a) `gearment.api.log` count increments by 1, (b) `sale_order_id` is set, (c) `http_status=400`, (d) `error_message` contains the URL. |
| **Owner** | next planner agent (chase Defect-05 in parallel) |
| **Blocks** | Defect-05 RCA visibility |
