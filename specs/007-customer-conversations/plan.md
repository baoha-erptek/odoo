# Implementation Plan: Customer Conversations (Pre-Sale & Post-Sale)

**Branch**: `007-customer-conversations` | **Date**: 2026-05-06 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/007-customer-conversations/spec.md`

## Summary

Surface customer messages — both pre-sale enquiries and post-sale conversation threads — inside Odoo's standard chatter so BA / customer-service operators stop context-switching between Etsy seller dashboard, Gmail, and Odoo. Two independent surfaces:

- **Post-sale** (`sale.order` chatter): inbound buyer messages tied to existing orders, sourced from Etsy API (preferred, gated on `conversations_r` scope) and email-parser fallback (works today). Dedup across channels via a small ledger model.
- **Pre-sale** (`multichannel.enquiry`): a lightweight new model on `multichannel_hub_core` that captures buyers contacting the shop **before** placing an order. `mail.alias` routes inbound emails; Etsy API picks up non-receipt-bound conversations once `conversations_r` is granted. Convert-to-Quote action spawns a draft `sale.order`.

Architectural decision (ADR-011): use a lightweight `multichannel.enquiry` model rather than adopt full `crm` dep, per research §R1.

## Technical Context

**Language/Version**: Python 3.12+ (Odoo 19 CE)
**Primary Dependencies**: Odoo 19 CE (`sale_management`, `stock`, `contacts`, `mail`); reuses `multichannel_hub_core`, `etsy_integration`. **No new third-party Python deps**. **`crm` NOT added** (ADR-011 decision).
**Storage**: PostgreSQL 16+ via Odoo ORM. Two new tables (`multichannel_enquiry`, `etsy_message_dedupe`) + chatter rows on `mail_message`.
**Testing**: Odoo `TransactionCase` + `HttpCase` for the mail.alias inbound flow. Two-phase testing per project memory (Phase 1 DB constraints, Phase 2 ORM behavior). Mocked `EtsyApiClient` for the conversation poller (mirrors P0-15/P0-16c pattern).
**Target Platform**: Odoo 19 CE on Linux (existing staging `https://odoo.hatafax.com` + production hosts).
**Project Type**: Odoo addon extension across `multichannel_hub_core` + `etsy_integration`.
**Performance Goals**: 10-min poll cycle posts ≤500 messages/cycle without exceeding Etsy rate budget; chatter post latency p95 < 200ms (uses standard `message_post`).
**Constraints**: Email-fallback path MUST work standalone (E1v2 still pending). PII-scrubbing required on all `etsy.api.log` writes. UNIQUE `(shop_id, etsy_message_id)` constraint must deploy via `init()` raw SQL per `project_sql_constraints_drift.md`.
**Scale/Scope**: ~15-19 active Etsy shops; estimated ~50-200 buyer messages/day across all shops; enquiry volume estimated 10-50/day. v1 covers User Stories 1 + 2; User Story 3 (outbound reply) deferred.

## Constitution Check

*GATE: Pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Compliance | Notes |
|---|---|---|
| I. Odoo-Native First | PASS | Uses `mail.thread`, `mail.activity.mixin`, `mail.alias`, `message_post()`, standard ACL groups. New `multichannel.enquiry` is a thin wrapper, not a parallel structure. |
| II. Email Parser Isolation | PASS | New email template lives in existing `email_parser.py` ORM-free service; chatter post happens in caller (`order_creator.py` extension), not parser. |
| III. Data Integrity First | PASS | Dedup via UNIQUE constraint; buffer/replay for messages-before-orders prevents silent loss; transactional `message_post`. |
| IV. Test-Driven Development | PASS (planned) | Each slice runs Phase 1 DB + Phase 2 ORM tests per playbook; `EtsyConversationPoller` tested with mocked client + JSON fixtures (no `vcrpy`, per P0-16 precedent). |
| V. Incremental Migration | PASS | Family C (post-sale) ships independently of Family D (pre-sale); each family has independently-shippable slices. |
| VI. Security by Default | PASS | OAuth tokens already in `ir.config_parameter` (P0-14 pattern reused). PII scrubbing inherited from P0-17 `etsy.api.log`. ACL gated on `sales_team.group_sale_user` + `multichannel_hub_core.group_ba_lead`. |
| VII. Simplicity Over Completeness | PASS | Email-template parsing accepts known fragility; raw email retained on parse fail; `multichannel.enquiry` chosen over full `crm` dep specifically to limit blast radius (ADR-011). |
